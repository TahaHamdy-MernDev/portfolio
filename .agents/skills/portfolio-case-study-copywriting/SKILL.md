# Portfolio Case-Study Copywriting

## When to use this
Trigger this skill any time you're writing, rewriting, or reviewing text for portfolio project pages (case studies, project descriptions, "the problem" sections, feature lists, role/challenge paragraphs) and site-wide copy. This applies to first drafts AND edits.

## Who reads this site
Every project page and section gets read by three very different audiences, often on the same day:
1. **HR / Recruiter** — Skims in 15 seconds, doesn't know internal framework mechanics, asks: *"Does this person build real things and can they explain them clearly?"*
2. **Business Stakeholder / Potential Client** — Asks: *"What real-world problem does this solve, and what did it make possible?"* Zero interest in stack lists.
3. **Developer / Technical Reviewer** — Demands proof of real engineering: a specific hard problem, an exact mechanism used to solve it, and evidence of understanding trade-offs.

**The failure mode to avoid:** Writing one paragraph that tries to serve all three simultaneously and ends up vague and buzzword-heavy for all three. Instead, structure the page so each reader gets what they need without wading through what they don't.

---

## The Core Problems to Eliminate (AI Cliché Patterns)
Check for every one of these on every review pass:

- **Stack Repetition**: The tech stack gets restated in the tagline, the problem section, the feature list, AND the role paragraph. It should appear in exactly ONE place (the Stack tag list / HUD). Everywhere else, name a technology only if the sentence is specifically about what that technology uniquely made possible.
- **Banned Filler Adjectives**: 
  `seamless`, `robust`, `powerful`, `cutting-edge`, `leverage`, `empower`, `streamline`, `comprehensive`, `scalable` (as a decorative buzzword rather than a concrete claim), `state-of-the-art`, `game-changing`.
  *Rule:* If a sentence still means the same thing after deleting the adjective, delete it.
- **Symmetrical Sentence Structure**: Three bullet points that all start with *"Implemented X to enable Y"* is an immediate tell. Vary sentence shape and length on purpose. Some bullets should be 4–6 words.
- **Restating the Obvious**: Don't explain what an ERP is, what B2B means, or what a dashboard is. Assume the reader either knows or doesn't care.
- **Vagueness / Hand-waving**: *"Handled complex business logic"* says nothing. *"Reconciled bulk courier COD payments against per-order settlement records, including partial-return reversals"* says something concrete. If a claim cannot be made concrete, cut it rather than pad it.
- **Generic Openers**: Never start a section with *"In today's fast-paced world"*, *"As businesses grow"*, or *"In the modern digital era"*. Start directly with the specific fact or problem.

---

## Multi-Audience Structure Per Project Page

- **Tagline (For Everyone)**: One clear sentence, zero tech jargon, easily understood by a non-technical relative. This is the HR and business layer.
- **The Problem (For Business + HR)**: 1–2 sentences, real-world operational framing, zero stack names.
- **Key Features (For Business + HR, skimmable by Developers)**: User-facing capabilities, active plain language, no stack names.
- **My Role & Technical Challenge (For Technical Reviewers)**: The *only* section allowed to dive into deep engineering. One specific problem, the exact mechanism used to solve it, and concrete numbers or trade-offs.
- **Stack Matrix (For Developers)**: Clean tag list in its dedicated matrix section, not repeated throughout narrative copy.

*Test:* If you remove the Stack tag section, a non-technical reader should be able to read the entire rest of the page and understand the product and its business value with zero comprehension loss.

---

## Tone and Voice
- Plain, declarative, confident. No hedging (*"might help"*, *"could potentially"*).
- Sentence case. No exclamation marks. No em-dash chains.
- First person, active voice: *"I built"*, *"I designed"*, *"I solved"* — never passive constructions like *"was responsible for the implementation of"*.
- Vary sentence length deliberately — a short punchy sentence after a detailed one reads like human writing.

---

## Self-Check Rubric (Run Silently Before Finalizing)
1. Does the tech stack appear more than once outside the Stack tags? → Cut duplicates.
2. Is any banned filler adjective present? → Cut or replace with a concrete detail.
3. Do 3+ consecutive bullets/sentences share the exact same grammatical rhythm? → Rewrite at least one.
4. Could a non-technical reader (HR, client) read the tagline + problem + features and understand the product? → If not, simplify.
5. Does the "technical challenge" name one SPECIFIC engineering problem (not "various challenges")? → If vague, ground it in the real code mechanism.
6. Could any sentence be copy-pasted onto an unrelated project just by swapping the noun? → If yes, rewrite it grounded in this specific system.
